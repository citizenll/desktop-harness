# Agent Note：Windows 原子替换会重试短暂的路径占用

Status: implemented

[English](2026-08-14-windows-atomic-rename-contention.md) | 中文

## 问题

`dsh-atomic-write` 过去只用一次 `rename(temp, target)` 发布暂存文件。Windows 上，读取方、索引器或安全扫描器可能短暂持有已有目标，libuv 会把这次替换报告为 `EACCES`、`EPERM` 或 `EBUSY`。设置浏览器场景在主题偏好提交期间读取 `settings.yaml`，暴露了这项故障：settings RPC 返回 `settings-rejected`，暂存文件被正确清理，旧文档保持不变，因此界面上看似已经选中的主题会在重载后丢失。这不是测试专属竞态；设置、凭据或已创作 preset 的任何共享文档都可能遇到无关的同用户读取方。

## 决策

`writeFileAtomic` 只围绕发布 rename 自己承担有界重试。Windows 上的 `EACCES`、`EPERM` 与 `EBUSY` 会保持同一份暂存文件和目标不动，以从 10 ms 增长到 100 ms 的退避重试，最长 2 秒。其他错误，以及其他平台上的任何 rename 错误，都会立即传播。期限届满时传播最后一次操作系统错误，既有的外层清理负责移除暂存文件。

调用方使用跨进程写入协议时，重试仍位于 `withFileLock` 内，因此等待发布期间，另一名遵循协议的写入方不能基于旧目标重新渲染。超时与退避是协议不变量，不是部署设置：它们吸收短暂的共享冲突，同时不会把持续存在的权限失败变成无界写入。

## 备选方案

- **串行化浏览器测试的读取。** 被拒绝，因为这只会把同一种共享冲突从测试里藏起来，杀毒软件、索引器、编辑器和其他本地读取方仍能在产品中触发它。
- **先删除目标再 rename，或退化为复制暂存内容。** 被拒绝，因为两者都会制造目标缺失或内容仅写入一部分的区间，放弃该原语最核心的原子替换保证；删除与 rename 之间崩溃还可能丢失最后一份可用文档。
- **重试提供方完整的读取-渲染-写入操作。** 被拒绝，因为暂存内容已经有效且受写锁保护。重新读取可能接纳不同的文档代际，还会重复并未失败的解析与渲染；占用发生在发布阶段，应由发布阶段处理。
- **把 `dsh-fs-local` 的 Koffi `ReplaceFileW` 路径移入零依赖实用包。** 针对此缺陷被拒绝：那条路径用于保留目标 DACL 与其他替换元数据，而共享 Harness-home 存储需要的是短暂共享冲突恢复。让每个 settings 与 credentials 安装都引入原生依赖，属于另一项 Windows 权限决策。

## 影响

短暂的 Windows 共享冲突不再丢弃设置、凭据或 preset 创作写入。持续存在的 Windows 冲突现在最多会晚 2 秒失败，随后调用方仍得到原始错误码与消息；POSIX 时序不变。单元测试注入全部三种可重试错误，证明非 Windows 失败不会重试，并把持续冲突推进到期限，同时检查旧目标仍在且没有残留 temp。浏览器主题场景在发布期间反复读取目标，从而覆盖真实 settings provider。
